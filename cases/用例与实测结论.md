# 用例与实测结论

每条结论都以实际跑过的结果为准。用例本身也必须被验证：危险类用例若复现不出预期的失败，
说明用例没造对，须重写或改归边界类，不得以"预期如此"入账。

| 用例 | 类别 | 实测结论 |
|---|---|---|
| `safe-item-lifetime` | 安全 | 两路逐 tick 哈希逐字节相同，600 帧无分歧。与基线相比首个分歧在 tick 1，唯一分歧层为 `ItemComponent`，正是补丁所改的组件 |
| `boundary-new-bcl-dependency` | 边界 | 补丁新增对 `System.Text.RegularExpressions.Regex` 的依赖，**未失败**，补丁路径正常跑完。补充 AOT 元数据之后这类新增依赖是可用的 |
| `danger-aot-references-hotupdate` | 危险 | 构建期失败，`GenerateStripedAOTDlls failed`，日志含 `Failed to resolve assembly: 'Brawler.ECS'`。补丁未能产出，不进入比对 |

## 边界用例的由来

`boundary-new-bcl-dependency` 原本是按"危险"设计的：设想补丁引入母包打包时没人用过的 BCL 类型，
会因代码裁剪而在运行期失败。实测推翻了这个设想——它照常工作。
按用例规则改归边界类，并记录实测所得。

这条否定结果本身有价值：对补丁安不安全的直觉经常是错的，只有真跑才知道，
而这正是本工具存在的理由。

## 危险用例的一次造假教训

`danger-aot-references-hotupdate` 的第一版只在母包侧源码加了一行 `using Brawler;`，
构建照常成功。原因是未实际使用该命名空间下的类型时，编译器不会在程序集里留下引用，
因而构不成依赖。第二版改为在母包侧的 MonoBehaviour 上放一个热更类型的字段，
才真正触发裁剪阶段的解析失败。

由此得出上面那条规则：危险用例必须实测复现出预期的失败才算数。
