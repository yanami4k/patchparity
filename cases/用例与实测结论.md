# 用例与实测结论

每条结论都以实际跑过的结果为准。用例本身也必须被验证：危险类用例若复现不出预期的失败，说明用例没造对，须重写或改归边界类，不得以"预期如此"入账。

除特别注明，以下结论均为 2026-10-11 在阿里云香港的 Windows 主机上，用命令行 `verify` 跑完整验证所得（默认场景：种子 42、600 帧、2 名玩家、无机器人）。机读的清单见 `cases.json`。

| 用例 | 类别 | 实测结论 |
|---|---|---|
| `safe-item-lifetime` | 安全 | 等价。与基线相比首个分歧在 tick 1，唯一分歧层为 `ItemComponent`，正是补丁所改的组件 |
| `safe-platform-speed` | 安全 | 等价 |
| `safe-gravity` | 安全 | 等价 |
| `safe-stock-count` | 安全 | 等价 |
| `danger-aot-random-edit` | 危险 | **不等价**：首个分歧 tick 0，分歧层 `TransformComponent`、`PhysicsBodyComponent`、`CharacterComponent`、`SpawnMarkerComponent`；确定性与覆盖自检均通过 |
| `danger-aot-api-signature` | 危险 | 补丁失败（运行期）：`MissingMethodException: MethodNotFind DeterministicRandom::FromSeed`，未进入整包重编 |
| `danger-aot-refs-hot` | 危险 | 整包重编失败（构建期，`GenerateStripedAOTDlls failed`）；补丁路径照常跑完 |
| `boundary-bcl-regex` | 边界 | 等价。补丁新增对 `Regex` 的依赖，照常运行 |
| `boundary-xml-assembly` | 边界 | 等价。补丁新增对 `System.Xml` 的依赖，照常运行；原按危险设计 |
| `boundary-item-new-field` | 边界 | 等价。热更侧组件新增字段 |
| `boundary-float-cast` | 边界 | 等价。运行时把越界浮点数转成整数并写进状态 |
| `boundary-filter5` | 边界 | 等价。改用母包里未出现过的 5 参数过滤器组合 |
| `boundary-field-reorder` | 边界 | 等价。调换组件字段顺序（2026-10-12） |

## 场景生成类（裁决 019）

这 5 道题改的代码在默认场景里根本不执行（默认场景移动速度为 0、没有地面）。每道题在默认场景与手工构造的探测场景下各实测一次（2026-10-12）。"可观测"指同一场景下整包重编与未打补丁的母包逐帧不同，即改动真的被执行到了。

| 用例 | 类别 | 默认场景 | 探测场景 |
|---|---|---|---|
| `search-safe-jump-speed` | 安全 | 等价，不可观测 | 等价，可观测（`ground=1;jump=200`） |
| `search-safe-move-formula` | 安全 | 等价，不可观测 | 等价，可观测（`moveSpeed=5`） |
| `search-safe-hit-reaction` | 安全 | 等价，不可观测 | 等价，可观测（地面、移动、贴身出生、频繁攻击、追逐） |
| `search-danger-curve` | 危险 | **等价（假阴性）**，不可观测 | **不等价**：首个分歧 tick 2，Transform、PhysicsBody |
| `search-danger-raycast` | 危险 | **等价（假阴性）**，不可观测 | **不等价**：首个分歧 tick 2，PhysicsBody、Character |

两道危险题都改的是母包里的框架代码：在默认场景下补丁与整包重编"一致"，只因为改动根本没被执行；换到能触发它的场景，不一致立刻暴露。没有可观测性检验，这两个危险改动会被当作安全放过。

## 由实测得出的几条认识

**两条路径都解释执行玩法代码。** 整包重编时，玩法程序集仍在热更清单里，同样以 DLL 由解释器加载。两条路径的差别只在母包一侧：AOT 程序集里的代码、HybridCLR 生成的桥接与元数据、裁剪保留了什么。所以只改玩法代码的"冒险写法"（浮点转换、新的泛型组合、新增字段、新的 BCL 依赖）全都等价；真正造成不一致的，是改动触及了母包。

**最危险的是改了母包里的代码。** `danger-aot-random-edit` 只改了框架里一个常数：补丁装得上、跑得完、两项自检都过，行为却与整包重编从第 0 帧起就不同。这是热更最隐蔽的一类事故——改动的一部分根本没随补丁下发，而补丁看起来一切正常。`danger-aot-refs-hot` 是同一类：补丁路径照常跑完，因为启动器的改动没随补丁生效；而整包重编连构建都过不了。

**新增 BCL 依赖在这个工程里是安全的。** `Regex` 与 `System.Xml` 两道都按"母包裁掉了、补丁会失败"设计，实测都照常运行，按规则改归边界。对补丁安不安全的直觉经常是错的，只有真跑才知道，这正是本工具存在的理由。

## 被淘汰的用例

- `boundary-struct-pack1`：把平台组件改成 `Pack = 1`。Klotho 的编译期分析器要求组件必须是 `Pack = 4`，报 `KLOTHO_STRUCT_LAYOUT_MISSING`，补丁编译不过——测的是框架的编码规则，不是热更，换成 `boundary-field-reorder`。

## 危险用例的一次造假教训

`danger-aot-refs-hot` 的第一版只在母包侧源码加了一行 `using Brawler;`，构建照常成功。原因是未实际使用该命名空间下的类型时，编译器不会在程序集里留下引用，因而构不成依赖。第二版改为在母包侧的 MonoBehaviour 上放一个热更类型的字段，才真正触发裁剪阶段的解析失败。

由此得出上面那条规则：危险用例必须实测复现出预期的失败才算数。
